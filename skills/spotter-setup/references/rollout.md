# 段階導入と誤検知チューニング

`spotter-setup` の手順 7〜10（生成 → 構文検証 → 空振りテスト → 段階導入）の詳細です。

## なぜ空振りテストが必須なのか

既存リポジトリに新規で `.spotter.yml` を導入すると、それまで誰も見ていなかった過去の
コミットや現在の作業ツリーに対して、いきなり検査が発動します。検証せずに置くと:

- `worktree` 粒度の検査（`doc-paths` / `consistency` / `doc-links`）は免除トレーラが
  無いため、誤検知があるとその場で詰みます
- `per-commit` 粒度の検査（`unwanted-files` / `commit-subject` / `diff-content` /
  `commit-intent` / `diff-size`）は、CI で過去のコミット全部に対して評価されると
  大量に落ちます
- どちらの場合も、対処療法として免除トレーラを乱発する運用が定着してしまい、
  spotter 導入の目的（免除は例外であるべき）を損ないます

## 手順7: 構文検証

```bash
spotter doctor --config <一時パス>
```

`checks.<key>.type` のタイプミス、必須フィールドの欠落、`command` 型の登録ミスなどを
ここで潰します。`spotter doctor` は検査一覧と起動粒度を表示するだけで、実際には検査を
実行しません。

## 手順8: 空振りテスト

```bash
spotter check --config <一時パス> --range HEAD~30..HEAD
```

`worktree` 粒度の検査は `--range` の値に関わらず現在の作業ツリーを見るので、これだけで
本番相当の判定が得られます。`per-commit`/`squashed` 粒度の検査は指定した範囲のコミットに
対して評価されます。範囲は最初は狭め（`HEAD~10..HEAD` 程度）から始め、問題が無ければ
広げて再確認してください（リポジトリの全履歴を一度に流すと出力が読みきれません）。

出力を検査ごとに分類します。

- **違反0件** → そのまま導入して良い
- **少数の違反、かつ内容が正当**（本当に直すべきものだった） → 導入して良い。ただし
  ユーザーに「この検査を入れると過去のこれこれが引っかかっていた」と一言伝える
- **大量の違反、または誤検知**（検査の意図と無関係なものまで引っかかる） → 手順9へ

## 手順9: 段階導入

誤検知が多い検査への対処は、検査ごとに次の順で検討してください。

1. **対象を絞る** — `doc-sync.pairs[].paths` や `companion-files.companions[].paths` を
   もっと狭いディレクトリに限定する（例: リポジトリ全体ではなくメインのソース
   ディレクトリ1つだけ）
2. **除外を足す** — `exclude` / `ignore` に、生成コード・vendor・テストフィクスチャなど
   検査の対象外にすべきパターンを追加する
3. **パターンを緩める** — `diff-content.deny[].pattern` や `commit-intent.rules[].deny_diff`
   が広すぎて意図しない行まで拾っている場合、より具体的な正規表現に絞る
4. **一旦外す** — 1〜3で誤検知が消えないなら、その検査は今回の導入から外し、
   `.spotter.yml` にコメントで理由を残す。後から改めて追加できます

どの検査から始めるべきかは `SKILL.md` の「検査を選ぶときの指針」を参照してください。
**最初から全ての組み込み検査を有効にする必要はありません。** 誤検知ゼロの検査だけで
始め、チームがトレーラの運用に慣れてから増やす方が定着します。

## `required_version` の固定

導入時点の `spotter --version` の出力をそのまま `required_version` に設定してください。

```yaml
required_version: v0.5.0
```

これにより、チームの誰かが古いバイナリで検査をすり抜けてしまう事故を防げます
（同梱されていれば `spotter-docs` スキルのバージョン固定ページに詳細があります）。

## 手順10: CI 連携の例

GitHub Actions の最小例（`spotter range` で比較対象の範囲を自動検出し、それを
`spotter check` に渡す）:

```yaml
- run: echo "RANGE=$(spotter range)" >> "$GITHUB_ENV"
- run: spotter check --config .spotter.yml --range "$RANGE"
```

GitLab CI やセルフホスト環境での自動検出の詳しいロジックとフォールバック条件は、
同梱されていれば `spotter-docs` スキルの CI 連携ページを参照してください。
